We've all been there building a personal project that just requires a little bit of auth, not a whole database or user system, but perhaps just a simple `PASSWORD` environment variable attached to the deploy.

This method always leaves me feeling a little uneasy as now I have to securely get this to my clients. I might shove it in a password manager, but if I'm deploying a shared-origin host like Cloudflare or Netlify, I might accidently autofill that on a different project.

Enter passkeys. This is a lot easier to set up than you might be thinking and we can retain just a single environment variable, but this time its information isn't sensitive at all.

The best part about implementing this is we'll learn how passkeys actually work together.

## Show me the money

Before we begin, let's explore what this looks like in practice. We'll add a passkey for this site, feel free to delete it later.

<PasskeyDemo />

So at a high level, what just happened?

1. We had the browser present a button to create a passkey, which ultimately presents a browser or OS-level creation screen.
2. Once the passkey is created, we told the browser to output the public part of its generated credential so that it could be copied.
3. Once copied to the server's environment variables, the server restarts.
4. Then we can visit the page once again, now seeing a login button.
5. Logging in uses a challenge provided by the server to prove that the public credential it now knows of was indeed created by us.

For those of us familiar with generating and using SSH keys, this process probably looks fairly familiar as its also a form of asymmetric cryptography.

Before we continue further, lets clean up the passkeys above so we can feel at ease as we take in the details.

## Let’s zoom in

### Passkey creation

Typically our passkey creation story would start on the server by generating a challenge to prevent [replay attacks](https://developer.mozilla.org/en-US/docs/Glossary/Replay_attack), but since we are saving the public credential by hand we will not need this protection.

Instead we can start by initiating the passkey creation process.

```js
const credential = await navigator.credentials.create({
  publicKey: {
    // Normally issued by the server, but random bytes 
    // will do for our usecase
    challenge: crypto.getRandomValues(new Uint8Array(32)),
    
    // The "relying party", which is the site this passkey 
    // belongs to
    rp: { name: location.origin },

    // Who the passkey is for, shown when picking a passkey 
    // to sign in with
    user: {
      id: crypto.getRandomValues(new Uint8Array(16)),
      name: "admin",
      displayName: "admin",
    },

    // Allow the browser to use its default algorithm
    pubKeyCredParams: [],
  },
});
```

Now we must extract the public portion of `credential` so it can be copied to the server. A reasonable way is to print it in Base64URL format, but this is up to the implementor.

```js
const publicKey = credential.response.getPublicKey();

element.textContent = new Uint8Array(publicKey).toBase64({
	alphabet: "base64url",
	omitPadding: true,
});
```

Finally, once this value is visible to the project owner, its up to them to add it to their server's environment variable store.  

It's good to know that the contents of this value are indeed public, and as such do not need to be treated as a secret.
